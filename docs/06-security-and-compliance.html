FinanceFlo Security & Compliance

Identity

Two separate identity systems

FinFlo runs two completely distinct identity systems so the business side and the customer side never share a session. Users are the business side — super_admin, admin, and staff — authenticated by the protect middleware under /api/auth. Members are the end-customers of the member portal, authenticated by protectMember under /api/member-auth, where req.member.user resolves to the owning business.

Every JWT carries a type claim, and each middleware rejects tokens of the wrong type — a member token can never reach a business route, and vice-versa. Tokens travel by Authorization: Bearer header on mobile and by the token cookie on web.

Why it matters

Separate middleware plus a typed token means a stolen or replayed credential is useless outside its own surface — business and customer authentication never cross.

Isolation

Multi-tenant isolation

Every business that signs up is an isolated tenant. Tenant data never mixes because every tenant-scoped query is scoped by the effective owner, not by the requesting user.

Effective owner scoping

The auth layer sets req.user.effectiveOwnerId — an admin's own id, or a staff member's ownerId. Tenant queries scope by it, never by req.user._id.

Branch narrowing

Branch managers are narrowed further by managedBranchId (cached on the User doc) so they see only their branch's data.

404, never 403

An unowned resource returns 404, not 403 — the platform never leaks the existence of another tenant's records.

Cascading attribution

Branch and owner changes cascade to every dependent collection so per-tenant and per-branch analytics stay correct.

Authorization

Role-based access control

Authorization is driven by Role documents, each carrying a permissions array. The platform resolves a user's permissions and gates routes against them, so access is data-driven rather than hardcoded.

Permission gates

Routes are gated with authorizePermissions('manage_x', …) — a request without the named permission is rejected.

Wildcard & bypass

The '*' wildcard and super_admin bypass all permission checks for platform operators.

Coarser helpers

The admin and staffOrAdmin helpers cover broad role gates where fine-grained permissions aren't needed.

Sessions

Session & auth hardening

Sessions are built to limit the blast radius of a compromised credential and to be revocable in real time.

Revocable sessions

Sessions can be revoked server-side; a revoked session is rejected on its next request and pushed off live sockets.

Short-lived web tokens

Web access tokens are short-lived (≈15 minutes) and native-safe, and are kept out of localStorage to reduce token theft.

Step-up re-auth

High-risk actions require step-up re-authentication, so an active session alone isn't enough for sensitive operations.

2FA & lockout

TOTP-based two-factor authentication and brute-force lockout protect the login surface; member sessions have parity with the same model.

Credentials

Password policy

Every password must be at least 8 characters and include at least one uppercase letter, one number, and one special character. The policy is enforced server-side on every password set, change, and reset endpoint — the server is the source of truth.

Min 8 characters 1 uppercase 1 number 1 special character
Client experience

The client surfaces the policy as a hint and shows a real-time strength meter as the user types — guidance on the front end, enforcement on the back end.

Data protection

Protecting personal data

Sensitive member data is encrypted at rest, and the API surface is hardened against common injection and tampering vectors.

Field-level encryption

Sensitive Member fields are encrypted at rest via encryptFields / decryptFields; the CNIC is stored encrypted with a hash for searchable per-tenant uniqueness.

Injection sanitization

Input is sanitized against NoSQL operator injection — $ and . keys are stripped from body, params, and query — and HPP protection blocks parameter pollution.

Transport & headers

helmet sets security headers and CORS is restricted; per-path rate limiting (auth / otp / signup / generic) throttles abuse.

Fail-closed startup

The server hard-fails on startup if JWT_SECRET is weak or short, or if MONGO_URI is missing — it refuses to run misconfigured.

Compliance & audit

Auditable by construction

FinFlo gives regulated lenders the controls and capabilities they need to meet KYC and AML obligations and to reconstruct any money movement after the fact.

KYC document vault

Member documents are held with explicit verification states (Pending / Verified / Rejected / Expired) so staff can confirm identity before activation.

AML / CTR monitoring

Anti-money-laundering and currency-transaction-report monitoring is built into the compliance pillar.

Full audit trail

The FinancialTransaction ledger records auditable money movement and ActivityLog records user actions — together a complete trail.

Expiry reminders

Document-expiry reminder jobs flag KYC documents before they lapse so records stay current.

Capabilities, not certifications

This document describes the security controls and compliance capabilities FinFlo provides. It does not assert any formal compliance certification or audit result.
